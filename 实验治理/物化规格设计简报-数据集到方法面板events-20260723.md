# 物化规格设计简报：数据集 → 方法面板 events（2026-07-23）

本简报供你（研究者）定义"数据集域 → 方法面板 `events`"的物化规格。这一步含论文建模决策，不由我代定；你填好第 5 节的模板后，我据此实现 bundle 物化器 + C2 sizing harness（冻结树代码，走批次流程 + 回归 + 重封基线）。

## 1. 为什么这是你的决策，不是胶水代码

项目里有两条平行的证据链：

- **IF 主方法链**（论文贡献）：`loaders → CanonicalObs → deviation_to_bpa → dst/BeliefState 时序融合`（见 `demo.py`）。产出 DST 质量 `Evidence`。
- **基准对比面板**（SHK-001B）：`methods/` 的 `B0–B5 + Proposed`，输入是结构化 `PublicEvent`（`events`）。

两条链的输入结构不同，且**没有任何代码把数据集域接到基准面板的 `events`**。测试里的 events 都是手写玩具数据；`benchmark/generator.py` 的 `Scenario.emit` 产出的是 IF 链的 `Evidence`，不是面板 `PublicEvent`。

"如何把 TEP/MIMII/HA4M/HM-SYNC 的原始观测变成带 `support/reliability/message_id/version/root_id/lineage/derived_from` 的证据事件"——这正是"人机料法环五证据流"的建模核心：它决定基准面板究竟在比什么。随手编一个映射会：(1) 替你冻结一个论文建模选择；(2) 用编出来的 bundle 尺寸驱动 C2→C3→整个 28-bundle 实验。故必须你来定。

## 2. 面板 events 的字段 schema（`methods/models.py`）

每个 event 是一个 JSON 对象，允许字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `message_id` | str | 是 | 消息标识（去重键之一） |
| `version` | int | 是 | 版本（去重键之一） |
| `root_id` | str | 是 | 证据所指的实体/根（设备/区域/流） |
| `support` | float∈[0,1] | 是 | 该证据对"风险"的支持度 |
| `reliability` | float∈[0,1] | 否（默认1.0） | 源可靠性折扣 |
| `lineage` | list[str] | 否 | 该证据的祖先链（最后一项为自身或直接前驱） |
| `derived_from` | list[str] | 否 | 直接派生自哪些 root |
| `order` | int | 否 | 段内到达/生成次序（并列打破用） |

bundle 顶层：`{bundle_id, algorithm_seed, transaction_id, events:[...], controls:[...]}`。

`controls`（仅 Proposed 用）：`{kind, roots, canonical_root?, replacement_root?, order}`，`kind ∈ {EQUIVALENCE, SUPERSEDE, MERGE, RETIRE, REPLAY}`。

## 3. 七个方法各自消费哪些字段（决定 bundle 必须populate什么才能区分方法）

核心信号 `effective = support × reliability`，所有方法都用。

| 方法 | 语义 | 关键依赖字段 |
|---|---|---|
| **B0** normalized_noisy_or | 基线 noisy-OR：`1−∏(1−eff)` | support, reliability |
| **B1** transport_exactly_once | 按 (message_id, version) 精确一次去重后 noisy-OR；同键异内容报错 | + message_id, version, order |
| **B2** lineage_ancestor_elimination | 去重后按 lineage/derived_from 消除祖先 root，仅保留叶子 | + lineage, derived_from, root_id |
| **B3** cautious_simple_support | 每 root 取最强证据，再取全局 max（Denœux cautious） | root_id（+ eff） |
| **B4** partial_dependence_strong_neighbor | 最强证据保留、其余按 ρ=0.70 打折后 noisy-OR | support, reliability |
| **B5** unknown_correlation_interval | 每 root 取max，输出 Fréchet 区间 [max, min(1,Σ)] | root_id |
| **Proposed** lifecycle_precombination | 去重 + union-find 按 derived_from/controls 归并规范根、处理 SUPERSEDE/RETIRE/MERGE/REPLAY 后再组合 | 全字段 + controls |

**关键含义**：若物化只产出"扁平、无 lineage、无 version 差异、无 controls"的事件，则 **B0=B1=B5 会塌缩为同一结果、B2 无祖先可消、Proposed 的生命周期逻辑完全不被触发**——基准就失去区分力。因此物化规格必须明确：五证据流如何生成 root 之间的派生/等价/取代/退役结构。这既是 sizing 代表性的前提，也是基准有效性的前提。

## 4. loader 现有可用原料

- `CanonicalObs`：`value[]`, `unit`, `t_gen`, `feature_of_interest`(实体), `procedure`(源/版本), `quality{}`。
- `deviation_to_bpa(score, prop_mask, ...)`：把偏离度 → `{P}` 类风险 BPA 质量（0–0.85）。每个 loader 有 `PROP_MASK`（TEP=16 工艺、其余域各自mask）与 `PROCEDURE` 串。
- TEP 已核验：`fit_normal(d00)` → `from_array(window=4)` 产 240 个 CanonicalObs（d01_te）。

可见的自然映射候选（**仅示例，待你确认或否决**）：`support ← deviation_to_bpa 的风险质量`；`root_id ← feature_of_interest`；`reliability ← 源可靠性账户（demo.py 里的 SourceReliability）`；`procedure ← message_id 前缀`。但 `version/lineage/derived_from/controls` 在 TEP 单流里没有天然来源——这正是需要你定义五证据流跨源关系的地方。

## 5. 待你填写的规格模板

请就以下逐项给出定义（可先只定 TEP，其余域后补）：

1. **bundle 边界**：一个 bundle = 什么？（如"一个 TEP 单元的一段 simulationRun"／"一个时间窗批次"）一个 bundle 含多少 events（数量级）？
2. **event 粒度**：一个 CanonicalObs 窗口 → 一个 event，还是聚合/展开？
3. **support 映射**：由 `deviation_to_bpa` 的哪个质量分量取？是否再归一？
4. **reliability 映射**：用 SourceReliability 账户？初值与更新规则？还是固定 1.0？
5. **root_id**：取 `feature_of_interest`？跨源如何对齐同一实体？
6. **message_id / version**：如何赋值？什么情况下产生"同 id 高 version"（B1 去重/重传语义要用到）？
7. **lineage / derived_from**：五证据流之间哪些是派生关系（如"法/流程证据派生自机/设备证据"）？没有则 B2/Proposed 退化，需你确认是否接受。
8. **controls（EQUIVALENCE/SUPERSEDE/MERGE/RETIRE/REPLAY）**：五证据流生命周期里哪些事件触发这些控制？（Proposed 的核心卖点，若全空则 Proposed 无法与 B 组区分）
9. **algorithm_seed / 多 seed**：每 bundle 跑几个 seed？（durable result 粒度是 bundle×method×seed）
10. **代表性域优先级**：C2 先用 TEP（已核验）；MIMII/HA4M/HM-SYNC 的物化是否复用同一映射，还是各域单独定义？
