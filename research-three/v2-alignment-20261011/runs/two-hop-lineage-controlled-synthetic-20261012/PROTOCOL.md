# Two-hop lineage replay: controlled synthetic protocol

**Status:** `FROZEN_PRE_RUN`. **Classification:** `CONTROLLED_SYNTHETIC_REPLAY_OF_SAVED_NORMALIZED_PUBLIC_SAMPLE`.

## Question and boundary

Can the existing source-lineage contract connect two offline, schema-changing aliases to the same locally saved normalized sample when both hop receipts are present, and return `UNKNOWN` when the second-hop receipt is missing? Compare that behavior with an exact-hash-only deduplication baseline.

This is one deterministic, CPU-only synthetic chain rooted in the previously saved public USGS normalized extract for `ci41346535`. The saved extract is an anchor only; the original USGS response bytes, collector receive time, and forwarding records are unavailable. Both aliases and all hop receipts are generated locally for this replay. Receipt validation means internal consistency under this runner, not source authenticity, historical transport, or statistical independence.

## Existing-data audit and denominator

No eligible production source-lineage replay log is present in this cloud checkout. The saved USGS audit records no exact local receive time, raw-body digest, or two-sided hop receipts. The prior V2 `LOCAL_RECEIPTS_V2.json` is generated by the same local runner and cannot serve as independent truth. The nearby `SHK-000-local-20260714T1655CST` ledger is labelled `G0_G2_SHAKEDOWN`, `confirmatory=false`, `claim_support=none`, and `GENERATED_NOT_EXECUTED`; it contains synthetic risk trajectories, not executed source-lineage replay records. Therefore the production-truth denominator is `0 available` and no production accuracy is calculated.

For a bounded software demonstration only, a separate scorer-side synthetic truth fixture declares that the three payload states in this one generated chain share one synthetic parent. The replay/validator does not read that fixture. Scoring counts three unordered pairs within the single chain; those pairs are dependent case rows, not three independent samples. No rate, confidence interval, significance test, or generalized effect estimate is reported.

## Frozen generator, split, and conditions

- **Source anchor:** exact bytes of `REAL_PUBLIC_FEED_SAMPLE.json`, bound by its frozen SHA-256 and byte count in `INPUTS.json`. This is the saved normalized sample, not the raw USGS response.
- **Split:** one fixed `SYNTHETIC-WORLD-001`; no randomization, development/held-out partition, tuning, or repeated worlds. The split is a controlled case fixture, not a sample design.
- **Hop 1:** construct a synthetic wrapper with outer ID `relay-one/<source feature ID>` and projection keys `record_ref`, `magnitude_value`, `location_text`, and `event_timestamp`.
- **Hop 2:** consume Hop 1 bytes and construct a second synthetic wrapper with outer ID `relay-two::<Hop-1 outer ID>` and projection keys `source_alias`, `summary`, and `updated_epoch_ms`.
- Each hop changes the outer ID and the projected schema. JSON is encoded as UTF-8, sorted-key compact JSON with one final newline. Transform inputs, outputs, code digest, and receipts are local-only.
- **Full-receipt condition:** include the synthetic source→Hop 1 and Hop 1→Hop 2 receipts.
- **Missing-intermediate-receipt condition:** retain the first receipt and omit the Hop 1→Hop 2 receipt from the verifier-visible set. The Hop 2 trace is marked incomplete.
- **Hash-only baseline:** bucket the three payload byte strings by exact SHA-256 equality. A unique hash is a separate dedup bucket; this baseline has no provenance evidence and must not be described as proving statistical independence.

## Frozen scoring rules

Evaluate the same three unordered pairs (`SOURCE/HOP1`, `SOURCE/HOP2`, `HOP1/HOP2`) in each condition against the separate synthetic truth fixture.

- `correct_source_attribution`: output identifies the shared synthetic ancestor.
- `wrong_separate_attribution`: output puts two truth-related records in separate hash buckets.
- `UNKNOWN`: the lineage contract cannot establish a complete chain.

Report raw counts per condition, including the fixed denominator of three pair rows and the single-world limit. Do not report percentages or treat pair rows as independent observations. The full receipt condition is predeclared to yield three shared-ancestor outputs; the missing-receipt condition should preserve only the source/Hop 1 shared ancestor and return `UNKNOWN` for pairs involving Hop 2; the hash-only baseline should create three distinct digest buckets. These are contract expectations, not an empirical production claim.

## Truth isolation and output order

The method runner reads only `INPUTS.json`, `PRE_RUN_MANIFEST.json`, the saved normalized sample, and the existing lineage contract. It does not read `SYNTHETIC_TRUTH_LOG.json`, `SCORER_TRUTH_MANIFEST.json`, or the scorer. It writes and hashes `METHOD_OUTPUTS.json` first. Only then does it check the frozen method-output expectations and write `RUNNER_CHECKS.json`. The separate scorer verifies that frozen hash and then reads the synthetic truth fixture to create `SCORED_RESULT.json`.

The truth sidecar, protocol, inputs, scorer, and method runner are all frozen before replay. The sidecar is explicitly synthetic, public in this repository, and used only for software-mechanics scoring; it is not an independent production log.

## Stop conditions and exclusions

Stop if the source sample hash changes, either alias projection differs from the frozen generator, required outputs are absent/duplicated, or the scorer cannot verify the method-output freeze. Keep unsupported lineage `UNKNOWN`; do not infer independence from different hashes or IDs. No NWS access, new collection, model/service, paid resource, live notifier, executor, or historical Mac run is involved.
