- **Status:** `FROZEN_BEFORE_EXECUTION`
- **Protocol version:** `same-root-vs-event-identity-2x2-v1.0.0`
- **Date:** 2026-10-11
- **Scope:** four synthetic scorer assignments, two unique method-input templates, one registered cutoff per template. This is a development pilot, not a formal effect evaluation or held-out test.

## Question and interpretation boundary

This pilot checks what the existing `TIME_ASSET_RULE` and `MULTI_EVIDENCE_RULE` emit when root-ID count is one or two. It separately assigns event identity and source dependence in a scorer-only ledger. The ledger assignments are not model inputs and do not claim that event truth can be inferred from the synthetic measurements.

The 2×2 dimensions are **hidden event relation** (`SAME` / `DIFFERENT`) and **visible unique acquisition-root count** (one / two). Root count is not used as a substitute for event identity or for a provenance audit:

- One root may carry observations from different events.
- Two root IDs may share an upstream source family and therefore be dependent.
- “Independent” in the method’s reason code means only that two root strings were counted. The method does not inspect the scorer-only source-family graph.

Each truth-opposite pair within a root-count row uses the exact same method-visible input template. If hashes confirm byte identity, both cases are `UNIDENTIFIABLE_FROM_METHOD_INPUTS` and are excluded from correctness/error-rate claims. A synthetic scorer label remains useful for exposing the information boundary; it must never be narrated as something the rules could have inferred.

## Scorer-only 2×2 assignment

`SCORER_ONLY_PREDECLARATION.json` freezes one hidden event registry and one hidden source-family graph, both assigned independently of the rule code and method-visible values. Relation is generated solely by event-registry identity: the pair is `SAME` iff both observation IDs map to the same predeclared event key; otherwise it is `DIFFERENT`. Source dependence is separately generated from source-family assignments. The assignments are fixed before method execution.

| Case | Input template | Hidden event assignment | Hidden source-family assignment | Pair label | Predeclared identifiability |
|---|---|---|---|---|---|
| `R1-SAME` | `V1_ONE_ROOT` | A=`EVENT-ONE-A`, B=`EVENT-ONE-A` | both observations=`FAMILY-ONE-STREAM` | SAME | unidentifiable; cloned with `R1-DIFF` |
| `R1-DIFF` | `V1_ONE_ROOT` | A=`EVENT-ONE-A`, B=`EVENT-ONE-B` | both observations=`FAMILY-ONE-STREAM` | DIFFERENT | unidentifiable; cloned with `R1-SAME` |
| `R2-SAME` | `V2_TWO_ROOT_IDS` | A=`EVENT-TWO-A`, B=`EVENT-TWO-A` | A=`FAMILY-TWO-A`, B=`FAMILY-TWO-B` (disjoint families) | SAME | unidentifiable; cloned with `R2-DIFF` |
| `R2-DIFF` | `V2_TWO_ROOT_IDS` | A=`EVENT-TWO-A`, B=`EVENT-TWO-B` | both observations=`FAMILY-TWO-COMMON` (shared upstream family) | DIFFERENT | unidentifiable; cloned with `R2-SAME` |

The scorer-only event registry is the synthetic truth-generation basis. It is not derived from asset match, timestamps, position, risk flags, method names, outputs, or root count. The source-family graph is a separate synthetic provenance basis: `R2-SAME` has two independent families; `R2-DIFF` has two distinct root IDs but one shared family. Both R2 cases have the same visible root strings. All four cases are marked unidentifiable because each opposite-label pair has identical method-visible bytes; no false-merge, false-split, accuracy, or superiority rate is computed.
