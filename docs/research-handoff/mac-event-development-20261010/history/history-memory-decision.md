# 历史台账与长期记忆：待决设计（不增加当前小试）

用户要求研究长期记忆或查数据库台账是否足够。当前设计候选：事件、整改、真假复核及纠正台账是事实源；按资产/隐患/时间与关系版本查询。结构化历史摘要仅为可重建、可失效的查询加速，附原记录ID、生成规则/版本及截止时间，不覆盖原事实，不把摘要再当独立来源重复融合。

是否引入LLM记忆须另有证据：何种信息无法通过结构化查询获得、是否改善判定、能否纠正撤回/追溯、引入错误与成本怎样评估。当前不调用LLM、不接数据库、不实现向量库。历史摘要由一组事件派生，不能因摘要+原事件同时存在便增信；过期摘要不能抹掉后续整改/证伪记录。查询不全属于信息缺口而非默认未整改。

后续H1/H2成对反例可同时对照直接台账查询与可重建摘要查询，在相同截止时间及信息下输出应一致；如果摘要省查询但不改变结论，收益归性能/呈现，不宣称推理创新。若LLM方案引入，需新范围与预算。本轮六轨迹和240计算/120秒/60CPU秒上限不变，Seatbelt阻断不变。

父任务资料调研后推荐数据库台账＋版本化结构化事件卡优先，独立LLM长期记忆暂不引入。原证据、真假核实、整改与复发分开；摘要引用来源版本、可纠正/失效/重建，旧模型判断或转述不是独立证据。后续只有字段查询遗漏自由文本案例或实测查询慢时才考虑语义检索/缓存。参考[Materialized View](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)、[Point-in-time joins](https://docs.feast.dev/getting-started/concepts/point-in-time-joins)，本轮仅接收父任务来源摘要，不宣称独立通读或实现。

防泄漏标签/历史查询必须同时限制physical event time与available/recorded-at time；事后补录的整改、证伪或关系纠正不得倒灌到更早前缀。重建摘要也需指定当时可知版本，而非只按事件发生时间过滤最新数据库。当前六条公开输入未包含历史查询，此要求纳后续H1/H2版本，不增加当前运行。
